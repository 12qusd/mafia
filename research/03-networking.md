# Networking & Backend Architecture Research

## Why the server must be authoritative

In a hidden-information game the only working defense is to NEVER transmit the secret. Anti-cheat, obfuscation, and encryption all fail because the cheat runs on the client, which must be able to decrypt whatever it receives — any data delivered to the client is readable via packet inspection or memory reads. Two case studies prove both directions: (1) Among Us used host-authoritative P2P-style architecture; role assignment happened on the host device, and clients received enough state that 'role reveal' / ESP mod menus were trivial and 'virtually undetectable' because they were pure client-side information reads. The 2020 cheating wave forced Innersloth into emergency server-side work (sources: pcgamer.com/of-course-there-are-already-among-us-cheaters/, burgercheats.com mod-menu listings, screenrant.com vent-hack coverage). (2) Town of Salem kept roles server-side: community/dev discussions confirm role-view 'hacks' don't work precisely because 'the client doesn't know the other player's roles' — but players did experiment with packet readers, so anything that IS sent is compromised (steamcommunity.com/app/334230 discussions threads on role-view hacks). Design rule: per-client need-to-know filtering at the serialization layer. Each client receives only: its own role/abilities, public game events (deaths, vote tallies as revealed by rules), chat channels it belongs to, and information its role has legitimately learned (e.g., investigator results). Night actions of other players are never echoed; faction chat is routed server-side only to faction members; vote/night resolution happens entirely server-side from queued intents. Subtle leaks to also close: side channels — if mafia clients receive extra messages or larger payloads at night than town clients, packet-size/timing analysis leaks faction; unify or pad per-phase message patterns. Also never embed the full role list in lobby payloads, never send 'you were targeted but protected' details beyond what rules reveal, and strip secrets from spectator and post-game data until game end. Academic backing: arxiv.org/pdf/2501.10881 (Addressing Network Packet-based Cheats in Multiplayer Games) treats packet-based hidden-info cheats as an architectural problem, not a detection problem.

## Recommended architecture

Two-tier split. TIER 1 — stateless lobby/matchmaking/auth service (plain HTTP/REST, horizontally scalable, no game state): handles login, party/queue, leaderboards reads, and issues a short-lived signed token {accountId, roomId} that admits the client to a specific game room. Also keeps a player→active-room registry so a restarted client can rediscover its in-progress game. TIER 2 — per-game room: one in-memory authoritative state machine instance per match (Colyseus 'Room' maps 1:1 to this; or a plain class in a Node process — at 50-500 CCU all rooms fit in one process). State machine phases: LOBBY → ROLE_ASSIGNMENT (single server-side seeded RNG; seed stored for audit/replay) → DAY_DISCUSSION → NOMINATION → TRIAL → VERDICT_VOTE → NIGHT (action queue collection) → NIGHT_RESOLUTION → check win → loop or GAME_OVER. Phase timers live server-side; on expiry the machine auto-transitions and applies defaults (abstain, no action) so a stalled/disconnected client can never block the game (pattern per mplgaming.com/server-authoritative-games/ and techtidesolutions.com/blog/game-server-architecture-basics/). NIGHT_RESOLUTION must be deterministic: collect all submitted intents into a queue during the night phase, validate each (alive? correct role? legal target? not roleblocked?), then resolve in a fixed published priority order (transports/roleblocks → protections → kills → investigations/info roles), producing an event list; this makes outcomes reproducible from (seed, intents) and enables replays and dispute audits. Message flow: client sends INTENTS only ({type:'vote', target}, {type:'night_action', target}, {type:'chat', channel, text}) → server validates against role+phase+alive status → mutates authoritative state → emits per-client FILTERED views (Colyseus StateView / boardgame.io playerView pattern: docs.colyseus.io/state/view, github.com/boardgameio/boardgame.io secret-state.md). Chat is just another server-routed channel: day chat broadcast to alive players, mafia chat only to mafia members, dead chat only to dead, whispers per game rules. Persistence boundary: live state in memory; append-only event log per match (for crash recovery, replays, ELO recompute, moderation evidence); transactional Postgres write of results at game end. Crash recovery via periodic snapshot or event-log replay is a nice-to-have at this scale, not a launch blocker.

## Transport options

### Plain WebSockets (Node ws/uWebSockets.js, or Go)

CORRECT CHOICE. A Mafia-style game is turn-based + chat: low message rate, no latency sensitivity below ~200ms, and TCP head-of-line blocking is irrelevant — exactly the profile where reliable ordered WebSocket transport is recommended (blog.algomaster.io/p/websocket-use-cases-system-design, techtidesolutions.com game-server-architecture-basics). One Node process trivially holds 500 concurrent sockets. TLS via Caddy/nginx reverse proxy. Node fits the dev's TypeScript profile better than Go here; Go buys nothing at this scale.

### Socket.IO on top of WebSockets

ACCEPTABLE. Adds rooms primitive (maps neatly to game/faction/dead chat channels), acks, auto-reconnect, and HTTP long-poll fallback. Costs: protocol overhead, and its room broadcast model still requires you to build the per-client state filtering yourself. The Redis adapter is only needed when scaling past one node — not needed at 500 CCU (socket.io/docs/v4/redis-adapter/, ably.com/topic/scaling-socketio). Reasonable DIY base, but Colyseus supersedes it for this genre.

### Steam networking / Steam Datagram Relay (SDR)

DEFER UNTIL A STEAM RELEASE, AND ONLY AS TRANSPORT. SDR relays traffic over Valve's backbone: hides server and player IPs, gives DoS protection, encrypted+authenticated, free if the game ships on Steam (partner.steamgames.com/doc/features/multiplayer/steamdatagramrelay, github.com/ValveSoftware/GameNetworkingSockets). But it is a transport layer into your own authoritative server — it does not change the authority model, requires Steamworks SDK integration and a matchmaking service issuing auth tickets, and is pointless for a web-first launch. If/when shipping on Steam, route Steam clients through SDR into the same room servers; web clients keep WebSockets.

### Peer-to-peer

NEVER ACCEPTABLE FOR THIS GENRE. Three independent disqualifiers: (1) hidden information — some peer must know all roles to arbitrate night resolution; whoever that is can cheat undetectably. This is exactly the Among Us host-authority failure: host-side role assignment enabled always-impostor mods and role-reveal ESP (pcgamer.com, screenrant.com). (2) IP exposure — peers learn each other's IPs, enabling DDoS/doxxing of players, uniquely toxic in a game whose core loop is accusing people. SDR exists largely to solve this for games that DO need P2P. (3) No trustworthy arbiter — votes, timers, and RNG can be manipulated by the host; host migration on rage-quit is unsolved pain. The bandwidth savings P2P offers are meaningless for a text game. There is no configuration in which P2P is acceptable here.

## Off-the-shelf frameworks

### Colyseus

BEST FIT — recommended. Open-source (MIT) Node/TypeScript authoritative multiplayer framework; Room abstraction maps 1:1 to a Mafia game; built-in matchmaking, room lifecycle, and binary delta state sync (colyseus.io, github.com/colyseus/colyseus). Critically for hidden information: StateView (v0.16+, replacing the old @filter decorators) provides per-client state filtering — @view()-tagged fields are only serialized to clients whose StateView includes them, explicitly designed for 'private fields' and 'team-owned data' (docs.colyseus.io/state/view, colyseus.io/blog/colyseus-016-is-here/). Built-in allowReconnection() with private per-client reconnection tokens (hardened after a sessionId-impersonation vuln, github.com/colyseus/colyseus/issues/354). Self-hosts on any Linux box; single process fine to ~thousands CCU; Redis-backed scaling exists when needed. Caveats: StateView not optimized for huge datasets (irrelevant for 15-player rooms); persistence/accounts are your own (good — dev wants Postgres); double-check that nothing secret sits outside view-filtered fields.

### Nakama (Heroic Labs)

CAPABLE BUT MISMATCHED. Apache-2 open-source Go server with batteries included: auth, friends, chat channels, leaderboards, matchmaking, authoritative match handlers in Go/Lua/TS runtime (github.com/heroiclabs/nakama). Friction for this dev: officially requires CockroachDB (Postgres only 'unofficially, dev environments only' per heroiclabs.com docs — though many run Postgres in prod anyway), authoritative match logic lives in Nakama's embedded runtime rather than a normal Node codebase, and the learning curve is widely reported as steep (saashub.com comparison). Self-hosts for ~$10/mo (snopekgames.com tutorial). Choose it only if the built-in social features (friends/chat/leaderboards) outweigh writing them yourself; per-client hidden-state filtering is still hand-rolled inside match handlers.

### Hathora

ELIMINATED — SERVICE SHUT DOWN. Hathora announced on 2026-03-04 that its game server hosting platform shuts down 2026-05-05; the company pivoted to AI inference infrastructure (team joined Fireworks AI). Verified via gameye.com/gameye-vs-hathora/. Do not build on it. Its niche (per-room container orchestration, Edgegap/Gameye as successors) is overkill for 50-500 CCU anyway — that's one VPS.

### PlayFab (Microsoft)

WRONG SHAPE FOR THIS DEV. Mature BaaS (since 2014): identity, economy, matchmaking, lobby, Party voice/chat; Standard/Premium tiers with $400/$8,000 of included usage meters then pay-as-you-go; dev mode capped at 1,000 lifetime accounts (playfab.com/pricing, learn.microsoft.com/en-us/gaming/playfab/pricing). But: no self-hosting (hard conflict with this dev's profile), Azure/C#-flavored ecosystem, usage-metered lock-in, and the actual game room logic still has to run on your own/Azure servers — PlayFab solves the parts (accounts, stats) this dev already does comfortably in Postgres. Skip.

### Raw Socket.IO (DIY)

VIABLE FALLBACK. Gives transport, rooms, acks, reconnect; you hand-roll room lifecycle, state machine, per-client filtered serialization, reconnection tokens, and matchmaking — i.e., you rebuild ~60% of Colyseus. Defensible if the dev wants zero framework magic and full control; otherwise Colyseus is the same stack with the hard parts done and audited (socket.io docs, dev.to/sauravmh/building-a-multiplayer-game-using-websockets-1n63).

### boardgame.io (bonus reference)

PATTERN DONOR, NOT A PLATFORM. Its playerView / PlayerView.STRIP_SECRETS is the canonical open-source implementation of server-side secret stripping for turn-based games (github.com/boardgameio/boardgame.io secret-state.md) — worth reading even if not adopted. Maintenance is sleepy and its multiplayer server is less production-hardened; note its issue #399 (secrets leaking via ctx._undo/_initial) as a cautionary tale: secrets leak through ANY unfiltered side path, not just main state.

## Persistence

Postgres for everything durable (matches dev profile; no reason for anything else at this scale). Live game state stays in room memory — DB is for identity, history, and moderation. Schema-level sketch: accounts(id, email, auth_provider+provider_id or password_hash, display_name, created_at, last_login); sessions(refresh tokens, device info); player_stats(account_id, mode, rating, rating_deviation, games_played, wins; consider per-role/per-faction win-rate columns or a side table) — prefer Glicko-2 over vanilla Elo for a multiplayer team game (rating deviation handles sparse play; compute team-vs-team expected outcome per faction); matches(id, mode, started_at, ended_at, settings_json, winner_faction, rng_seed); match_players(match_id, account_id, seat, role, faction, outcome, rating_before, rating_after, left_early bool); match_events(match_id, seq, ts, type, payload JSONB, append-only) — this event log is triple-duty: replays, deterministic ELO/result recomputation, and moderation evidence; chat_messages either inside match_events or its own table (account_id, match_id, channel, text, ts) with a retention policy column/partitioning by month for cheap deletion; reports(id, reporter_id, reported_id, match_id, category, message_refs, free_text, status, resolution, resolved_by, created_at/resolved_at); sanctions(id, account_id, type[mute|ban|chat_ban], scope, reason, issuer_id, created_at, expires_at NULL=permanent) — checked at login and room-join; enforce mutes server-side in the chat path. Ranked queue can live in-process or Redis, but at 500 CCU an in-memory queue with Postgres write-through is fine; Postgres LISTEN/NOTIFY covers cross-service pokes. Write match results in one transaction at game end (matches + match_players + rating updates). GDPR hook: account deletion anonymizes account row and match_players linkage but keeps aggregate/match integrity (replace with tombstone id).

## Hosting costs

Cheap — this genre is text-plus-timers. 500 CCU ≈ ~35-50 concurrent rooms; per-client traffic is well under 1 KB/s with bursts at phase changes; a single Node process on 2 vCPU handles it with headroom. Realistic self-host stack (fits dev's existing Linux habits): 1× Hetzner CPX21/CCX13-class VPS (2-4 vCPU, 4-8 GB) for lobby+rooms: €8-15/mo (hetzner.com/cloud — entry instances from €3.49; 300-500 Mbit and ~20 TB traffic included, far beyond need); Postgres on the same box or a second small VPS: €0-10/mo; backups/object storage: €1-5/mo; TLS free (Let's Encrypt/Caddy); Cloudflare free tier in front of the lobby HTTP API for basic DDoS posture (game WebSocket connects direct or via proxied hostname). Total: roughly €15-40/mo (~$20-50). Comfort ceiling with managed Postgres (DO/Supabase ~$15-25/mo), a staging box, and uptime monitoring: $50-100/mo. At 50 CCU it's one $5-8 VPS. Per-room orchestration platforms are unjustified at this scale (and Hathora, the obvious one, shut down May 2026; Edgegap-style pricing ~$0.00115/min/vCPU only makes sense for latency-sensitive global session games). Cost only inflects past ~5-10k CCU, when you'd shard rooms across processes/boxes — a process-per-shard model the room architecture already permits. The dev's own hardware (existing fleet) could host this at ~$0 marginal, but a rented VPS gives clean IP reputation and keeps player traffic off the home/office network.

## Reconnection

Disconnects are routine (mobile networks, tab closes) and in this genre a disconnect must neither forfeit the game nor leak anything. Pattern (Colyseus has it built-in; replicate if DIY): (1) On socket drop, keep the player's seat and mark them 'disconnected' with a grace window — 60-120s or until current phase end, whichever is longer; other players see only a connectivity badge. (2) Reconnection auth uses a PRIVATE per-session reconnection token issued at join and ROTATED on every reconnect — Colyseus moved to this after a real vulnerability where knowing a victim's sessionId+roomId let an attacker reconnect as them and act on their behalf (github.com/colyseus/colyseus/issues/354). If hand-rolling: token is secret, single-use, bound to accountId+roomId. (3) On resume, the server sends a FULL fresh filtered snapshot for that client (their role, everything their role has learned, vote state, chat history for channels they belong to, current phase + remaining timer) — never trust or diff against the client's stale state; chat backfill bounded to the current match. (4) The stateless lobby keeps player→active-room mapping, so a fully restarted client can ask 'am I in a game?' and rejoin after app restart, not just socket blips. (5) Timer policy: phase timers never pause for disconnects; on expiry the state machine applies defaults (abstain, no night action) — the game always advances. (6) Abandonment policy for ranked: Colyseus allowReconnection('manual') supports custom logic like 'reject if player missed >2 rounds' (0-15-x.docs.colyseus.io/server/room/); convert to abandon + loss + escalating queue penalty after N missed phases. (7) Heartbeat ping/pong to detect half-open TCP promptly. Socket.IO's auto-reconnect handles transport retry but NOT identity/state resume — the token+snapshot layer is yours regardless of transport.

## Moderation

Minimum viable set for launch (social deduction chat is high-toxicity by construction — accusation is the core loop): (1) REPORTS: in-game report attached to match_id + specific message/event refs, with category picklist + free text. Shape it DSA Article 16-style from day one since EU users are likely: user-accessible flagging with substantiated reason and exact content location; store the report; notify both reporter and affected user of the decision; target ~72h human-review turnaround; maintain a monitored human contact point (blog.promise.legal/eu-digital-services-act-game-studios/, ggwp.com/the-digital-services-act/). Because the server logged the authoritative match_events stream, every report comes with verifiable evidence — no client screenshots needed. (2) MUTES/SANCTIONS: enforced server-side in the chat path (drop at server; never trust client-side hiding); sanctions table drives mute/chat-ban/account-ban checks at login and room-join; escalating durations; ban appeals path recommended (DSA pressure on unexplained bans is increasing — esportslegal.news 2025 coverage of gaming bans under DSA). (3) PROFANITY FILTER: server-side pass on every message before broadcast; use a maintained evasion-aware library (e.g., 'obscenity' on npm handles leetspeak/spacing tricks) rather than a naive regex list; launch policy: mask matches + keep report path, optionally let users toggle display filtering client-side — but the canonical stored log keeps the original for moderation. (4) LOG RETENTION (GDPR-ish): chat logs tied to accounts are personal data (gdpreu.org gaming-harassment analysis). No fixed statutory period — retention must match stated purpose (EDPB Guidelines 3/2025 on DSA/GDPR interplay). Practical policy: 30-90 days hot retention of chat/match logs for moderation purposes; logs referenced by open reports or active sanctions are retained until resolution + appeal window; then delete or anonymize; document this in the privacy policy; support access/export/erasure requests; partition chat tables by month so deletion is a DROP, not a scan. Defer to post-launch: ML toxicity scoring, voice, trust-score matchmaking.

## Bottom line

Build server-authoritative from line one: Colyseus (Node/TypeScript) self-hosted on a single Hetzner-class Linux VPS, plain WebSockets behind Caddy/nginx TLS, stateless HTTP lobby/auth service issuing signed room tokens, one Colyseus Room per match running an explicit phase state machine with server-side timers, queued night intents, and deterministic seeded resolution. Use StateView per-client filtering so secret roles, night actions, and faction chat are never serialized to unauthorized clients — this single architectural choice is what killed role-reveal cheats in Town of Salem and what Among Us lacked. Postgres for accounts, Glicko-2 ratings, match history (append-only match_events JSONB log), reports, and sanctions. Reconnection via Colyseus allowReconnection with private rotated tokens + full filtered snapshot on resume; phase timers never pause. Launch moderation: server-side mutes, evasion-aware profanity masking ('obscenity'), DSA-style report queue with 30-90 day log retention. Rejected: P2P (categorically — hidden info + IP exposure + no arbiter), Hathora (shut down 2026-05-05), PlayFab (no self-host, lock-in, wrong stack), Nakama (CockroachDB/Go runtime friction; only reconsider if built-in friends/chat/leaderboards become must-haves), raw Socket.IO (viable but rebuilds Colyseus by hand). Add Steam Datagram Relay later only as an additional transport into the same authoritative rooms if shipping on Steam (free, hides IPs, DDoS protection). Expected cost: ~$20-50/mo through 500 CCU; the architecture shards by room/process when growth demands it.
